# CLAUDE.md

Site estático Jekyll — blog pessoal do Felipe Toscano, conteúdo em português (pt-BR), publicado em https://felipetoscano.com.br via GitHub Pages. Ver README.md para visão geral de stack e estrutura.

## Ambiente

Ruby/Bundler normalmente **não** está instalado neste tipo de sandbox — rode `ruby -v` antes de tentar buildar, em vez de assumir; sem sudo sem senha e sem headers de build (libssl-dev etc.) não dá pra compilar um Ruby aqui. Node **pode** ser obtido sem root via tarball portátil oficial (`nodejs.org/dist/`) — assim dá pra rodar `npm install`/`npx gulp <task>` de verdade para validar mudanças no gulpfile. Não há suíte de testes (`npm test` é um placeholder no-op). CI/deploy roda via `.github/workflows/jekyll-gh-pages.yml` (GitHub Actions) a cada push em `master`.

## Comandos

- `bundle exec jekyll serve` — build + servidor local, só o Jekyll (precisa da gem `webrick` no Gemfile em Ruby >= 3.0; já está lá)
- `gulp` — pipeline completo: compila Stylus (`src/styl` → `assets/css/main.css`), compila/concatena JS (`src/js` → `assets/js/main.js`), builda o Jekyll e sobe browser-sync com live-reload. Config em `gulpfile.mjs` (ESM, API do Gulp 5 — `gulp.series`/`gulp.parallel`, sem arrays de dependência do Gulp 3)
- `./initpost.sh -c Título` — cria `_posts/AAAA-MM-DD-titulo.md` com o front-matter padrão
- `./initdraft.sh -c Título` — mesma coisa em `_drafts/` (não publicado, ignorado pelo git)
- `gulp webp` — gera `.webp` (via `sharp`) a partir de cada PNG/JPG em `assets/img/posts/` e de `assets/img/blog-author.png`, **e apaga o PNG/JPG original logo em seguida** (só o `.webp` fica pra commitar). Rodar depois de adicionar/trocar a imagem de capa (`image:`) de um post — ver "Otimização de carregamento de imagem" abaixo.

## Otimização de carregamento de imagem (sessão 2026-08-12)

- **`assets/img/posts/*.png|jpg` (capas dos 88 posts, ~9,8MB) foram convertidas pra `.webp` com `sharp` (`gulp webp`, qualidade 82, sem redimensionar) e os PNG/JPG originais foram apagados** — só o `.webp` existe hoje no repo (~1,4MB total, ~86% menor), conferido visualmente numa amostra sem perda perceptível. `assets/img/blog-author.png` (avatar) seguiu o mesmo caminho → `assets/img/blog-author.webp`. **Não sobrou fallback PNG/JPG**: `<picture>`/`<source>` foi removido dos templates, é `<img>` direto pro `.webp`. Os originais continuam recuperáveis pelo histórico do git (estavam commitados antes desta sessão) se algum dia precisar. `assets/img/blog-image.png` (logo, 10KB, usado só num `<img>` oculto de schema.org) **não** entrou nessa conversão — ficou de fora do escopo por ser baixo valor, continua PNG.
- **Front-matter `image:` dos 88 posts e `_config.yml` → `logo:` foram atualizados de `.png`/`.jpg` para `.webp`** — necessário porque `jekyll-seo-tag` lê `page.image`/`site.logo` direto do front-matter/config pra montar `og:image`/`twitter:image`/o `logo` do JSON-LD, sem passar pelos templates. Se esses campos continuassem apontando pro PNG apagado, os preview de link (Twitter/Facebook/LinkedIn/WhatsApp) e o JSON-LD ficariam quebrados. Não houve como validar isso num crawler real (sem Ruby/build local); os principais crawlers de OG suportam WebP normalmente hoje, mas vale conferir um preview de link depois do primeiro deploy.
- **Todo post novo deve referenciar a capa como `.webp` desde o front-matter.** Fluxo: salvar a capa (PNG/JPG normalmente) em `assets/img/posts/<slug>.png`, colocar `image: '/assets/img/posts/<slug>.webp'` no front-matter (a extensão final, antes mesmo do arquivo existir), rodar `gulp webp` (converte e apaga o PNG automaticamente) e commitar só o `.webp` resultante. Esquecer de trocar a extensão no front-matter depois de rodar `gulp webp` — ou commitar um PNG/JPG novo sem rodar a task antes — é o jeito de quebrar isso.
- **`loading`/`decoding`/`fetchpriority` nativos do navegador substituíram o lazy-load caseiro da home.** `index.md` tinha um hack de 2013 (placeholder.png + `data-url` + scroll listener em `src/js/scrollanimation.js`) que baixava um placeholder E a imagem real via JS. Removido: a home agora usa `<img loading="eager" fetchpriority="high">` só na primeira capa (LCP) e `loading="lazy"` nas demais; `post.html` usa `eager`+`fetchpriority="high"` na capa (hero acima da dobra). `assets/img/placeholder.png`, `assets/img/icons/preloader.svg`, a classe `.preload` (`src/styl/_home.styl`) e a função `loadImageUrl`/suas chamadas (`src/js/scrollanimation.js`) foram removidos por ficarem órfãos — `scrollanimation.js` continua existindo só para a animação de fade-in on-scroll dos cards (`shown`/`animate`), que é independente disso.
- **`width="600" height="315"` fixo nas tags `<img>` de capa** (post-cover, thumbnails da home, avatar com suas próprias dimensões 200×200) — o CSS já força `width:100%; height:auto` nesses containers, então esses atributos só existem para o navegador reservar a proporção certa antes da imagem carregar (evita layout shift), nunca para forçar um tamanho fixo. Válido porque **todas** as capas hoje compartilham a mesma proporção 1.905:1 confirmada via `sharp`; se um post novo usar uma capa com proporção diferente, o espaço reservado vai ficar levemente errado (CLS pequeno), não quebra nada.
- **`_plugins/lazy_images.rb` (novo) adiciona `loading="lazy" decoding="async"` via regex a qualquer `<img>` do HTML já renderizado que ainda não declare `loading=`.** Cobre as ~21 imagens inseridas via Markdown no corpo dos posts (`![alt](src)`, boa parte hotlinked de CDNs externos como Cloudinary — fora do alcance do `gulp webp`, continuam PNG/JPG hotlinked mesmo), que não têm como receber o atributo na sintaxe do Kramdown. Não toca as tags que os templates já marcam explicitamente (post-cover `eager`, avatar `lazy`). Plugin custom em `_plugins/` só funciona porque o deploy usa `bundle exec jekyll build` direto (`.github/workflows/jekyll-gh-pages.yml`), não o build legado `safe: true` da gem `github-pages` (que bloqueia plugins arbitrários).
- **Bug real já causado por esse plugin: a 1ª linha de um arquivo `.rb` não pode conter o texto `coding=` nem `coding:`, nem "escondido" dentro de outra palavra.** A primeira versão do arquivo começava com um comentário contendo `decoding="async"` — o parser do Ruby escaneia a primeira linha de comentário atrás de um magic comment de encoding (`# coding: xxx`, mesma regra do PEP 263 do Python), casou `coding=` dentro de `de`+`coding=` e tentou usar `"async"` como nome de encoding, quebrando o build inteiro no CI com `unknown encoding name:  (ArgumentError)` antes de qualquer linha de código rodar (só a 1ª linha é escaneada, ou a 2ª se a 1ª for shebang `#!`; da 2ª linha em diante o texto é livre). Corrigido reescrevendo a linha 1 sem esse padrão. Esse é o motivo de esta seção não citar mais "não testado localmente" pro plugin — foi testado de verdade no CI e falhou uma vez.
- `sharp` foi adicionado a `package.json` (`devDependencies`) — único pacote novo desta sessão; ver bullet do `imagemin` acima sobre vulnerabilidades.

## Séries de posts tutoriais (numpy/pandas/python/matplotlib) — convenções (sessão 2026-09-25)

- **Front-matter padrão de um post de série tutorial**: `title: "<Tema> | #N - Título da Parte"` (numeração sequencial da série, não do blog inteiro; `<Tema>` identifica a série antes mesmo de abrir o post — ver tabela de temas abaixo); `date:` no mesmo dia "de publicação" da leva, com horário incremental (ex. 20 em 20 min) simulando ordem de leitura; `image: '/assets/img/posts/<slug-do-arquivo-sem-data>.webp'`; `description:` uma frase de prosa; `category: 'ciência de dados'` (numpy/pandas/matplotlib/machine learning) ou `'dev'` (tutorial Python "puro"/estruturas de dados e algoritmos); `tags:` lista fixa de 4 itens por biblioteca — Matplotlib: `Ciência de Dados, Python, Programação, Matplotlib`; Pandas: idem trocando a última por `Pandas`; NumPy (posts de 2026, não os de 2019): idem trocando por `Numpy`, sem a tag extra `Data Science` que só os posts antigos usavam; `twitter_text:` o título sem o prefixo `"<Tema> | #N -"`; `introduction:` uma frase "Nesta parte do tutorial, você vai...". Corpo: intro sem heading (1-2 parágrafos, tom de conversa) → seções `##`/`###` com exemplos numerados ("Exemplo N - ...") → bloco de código seguido de um parágrafo explicando o resultado (sem bloco de saída separado nos posts de Matplotlib, já que `plt.show()` não imprime texto) → `> **Nota:**` pontual → fechamento com 1-2 frases de ponte pro próximo post → linha final `**Fonte adaptada:** [links]`. Tamanho-alvo: 120-300 linhas / 800-1600 palavras (média real ~1000-1100 palavras nos posts de 2026-08-11).
- **Tabela `<Tema>` → série (padronizado na sessão 2026-09-25, aplicado retroativamente aos 82 posts das 6 séries "atuais" + aos 19 posts da série MongoDB)**: `NumPy` (posts `numpy-com-python-*`, 2026 — não os de 2019, ver abaixo), `Pandas` (`pandas-*`), `Matplotlib` (`matplotlib-*`), `Python` (`tutorial-python-*`), `Estruturas de Dados` (`dsa-*`), `Machine Learning` (`ml-*`), `MongoDB` (`category: 'bd'`, 19 posts de 2014-2015 — nomes de arquivo não são uniformes, os 3 primeiros da série (`#1`–`#3`) não terminam em `-no-mongodb.md` como os demais). Antes de usar um `<Tema>` novo pra uma série, conferir se esse tema já numera `#1` em outra série existente (ex. os dois grupos de NumPy) — reaplicar o mesmo `<Tema>` numa numeração que reinicia geraria dois posts com título colidindo até o `-`; nesse caso, avisar o usuário antes de escolher/aplicar o prefixo.
- **Exceção deliberada — só o NumPy legado de 2019 ficou fora dessa migração**: 8 posts (com a tag extra `Data Science`) continuam com `title: "#N - ..."` sem prefixo de tema — decisão do usuário pra evitar colisão de numeração com o NumPy novo (ambos reiniciam em `#1`; a série MongoDB, sem esse problema, já foi migrada). Não migrar esse grupo retroativamente sem confirmar de novo com o usuário; um post novo nessa série antiga (pouco provável, mas possível) deve seguir o estilo antigo já em uso ali (`"#N - ..."` sem tema), não o padrão novo.
- **Ao inserir um post novo NO MEIO de uma série numerada já publicada** (não só anexar no final): renumerar o `#N` do `title` de todo post que muda de posição (mantendo o prefixo `<Tema> | ` intacto); reajustar o horário em `date:` mantendo o mesmo dia do prefixo do nome do arquivo (o `YYYY-MM-DD-` do filename não precisa mudar, só a hora no front-matter — o Jekyll usa a data do front-matter como data efetiva de ordenação); e reescrever as frases de abertura/fechamento ("no post anterior...", "no próximo post...") dos posts vizinhos pra manter a costura narrativa coerente com a nova ordem. Sempre confirmar com o usuário se o reordenamento de data deve valer só pra série em questão ou pro blog inteiro — mexer em datas de posts de séries não relacionadas (ex. MongoDB de 2014) reescreveria histórico já publicado sem necessidade.
- **Citações "Fonte adaptada"**: os posts de tutorial citam W3Schools (séries/posts mais básicos) ou TutorialsPoint (séries/posts mais avançados) — nunca a documentação oficial (`matplotlib.org`, `numpy.org` etc.), exceto quando não existe capítulo equivalente na fonte de costume (ex.: `rcParams` do Matplotlib não tem capítulo dedicado no TutorialsPoint; usar a doc oficial só nesse tipo de lacuna). **Nunca inventar a URL de um capítulo específico** — o slug de uma página do TutorialsPoint costuma ser adivinhável errado (ex.: é `matplotlib_filled_plots.htm`, não `matplotlib_filled_area_plot.htm`; é `matplotlib_polar_charts.htm`, não `matplotlib_polar_plot.htm`). Antes de citar, verificar a URL de verdade (WebFetch na página-índice do tutorial, ex. `tutorialspoint.com/matplotlib/index.htm`, que lista todos os capítulos com os links reais).

## Geração de imagem de capa sem Ruby/ferramenta de design (sessão 2026-09-25)

- Este sandbox não tem Ruby (ver "Ambiente") nem nenhuma ferramenta de geração de imagem por IA — mas **Python 3 com Pillow (PIL) está disponível** e consegue desenhar e salvar `.webp` diretamente (`Image.save(caminho, "WEBP", quality=82)`), sem depender do `gulp webp`/`sharp` pra esse caso específico (o `gulp webp` continua sendo o fluxo padrão pra quando o usuário fornece a arte já pronta em PNG/JPG).
- **O design system das capas atuais (88 posts, 600×315px) é vetorial/geométrico e 100% reproduzível por código** — não é arte fotográfica nem plausível de recriar bem com um gerador de imagem genérico (erraria o estilo minimalista exato). Receita confirmada por amostragem de pixel nas imagens reais:
  - Fundo: gradiente diagonal simples do canto superior-esquerdo `rgb(13,59,84)` até o canto inferior-direito `rgb(33,115,169)`, interpolado linearmente por `(x+y)/(largura+altura)`.
  - Brilho quente sobreposto: "glow" radial centrado perto de `(0.72×largura, 0.10×altura)`, raio ~230px, cor `rgb(255,214,150)` (creme), misturado por interpolação linear com força ~35% e falloff `(1 - dist/raio)^1.6`.
  - Textura: pontos brancos semitransparentes (~16% opacidade, raio ~1.4px) numa grade regular de ~26px sobre o gradiente.
  - Ícone: sempre em traço branco (`rgb(255,255,255)`, largura ~6-7px, com círculos do mesmo raio nos vértices/pontas simulando "rounded cap/join", já que `ImageDraw.line` do Pillow não arredonda ponta sozinho) representando o conceito central do post, com **um único destaque em laranja sólido e opaco** `rgb(243,174,70)` — nunca laranja semitransparente direto sobre o fundo azul, porque o alpha-blend resulta numa cor "suja" (oliva/amarronzada) fora do padrão visual do site. Variar a opacidade do laranja só é aceitável quando é intencional pra simular uma escala (ex. célula de mapa de calor); o elemento de destaque principal de cada ícone continua sempre opaco.
  - Cada ícone deve representar visualmente o tópico central do post específico (ex.: área preenchida sob uma curva pra `fill_between`; um frame dividido em células com uma em destaque laranja pra layouts de subplot; um radar/gráfico polar pra coordenadas polares; uma grade 3×3 com opacidades variadas pra mapa de calor) — não reusar o ícone genérico de "gráfico de linha" pra tudo.
  - Depois de gerado, comparar visualmente (`Read` da imagem) contra 1-2 capas existentes da mesma série antes de aceitar, e checar que o tamanho do arquivo fica na mesma faixa das capas existentes (hoje, ~4-11KB por imagem em 600×315).

## Pontos de atenção (já causaram bugs reais neste repo)

- **`_config.yml` → `url:`**: precisa ficar descomentada, apontando para `https://felipetoscano.com.br`. Ficou comentada por acidente a partir de um commit de teste em 2019 e nunca foi revertida — quebrou silenciosamente `sitemap.xml`, `feed.xml`, as tags `canonical`/`og:url`/`twitter:image` e os botões de compartilhar (Twitter/Facebook), que dependem de `site.url`. Corrigido nesta sessão; não comentar essa linha de novo.
- **Front-matter `category:` dos posts**: as páginas de arquivo (`bd.html`, `dev.html`, `ciencia-de-dados.html`, `github.html`) filtram com `{% if post.category == page.category %}` — comparação exata e sensível a maiúsculas/acentos/whitespace. Um post com `category: 'Ciência de Dados'` (maiúsculo) já ficou de fora da listagem porque a página usa `'ciência de dados'` minúsculo. Usar sempre um destes valores exatos: `bd`, `dev`, `ciência de dados`, `github`.
- **Final de linha (CRLF) em posts antigos**: 11 posts da série MongoDB (2014-2015) tinham o arquivo inteiro em CRLF, o que contaminava o valor de `category:` com um `\r` invisível e os sumia da respectiva página de arquivo — mesmo efeito do bug acima, só que invisível ao abrir o arquivo. Já normalizados para LF nesta sessão. Manter LF em posts novos/editados.
- **`assets/css/` e `assets/js/` são compilados a partir de `src/` e versionados no git.** O workflow de deploy builda só o Jekyll — nunca roda `gulp`. Depois de editar `src/styl/` ou `src/js/`, rodar `gulp` localmente e commitar os arquivos gerados em `assets/`, senão o site publicado não reflete a mudança.
- **Gems fixadas no Gemfile precisam respeitar os `depends_on` das gems que já as puxam transitivamente.** `jekyll ~> 4.4` já depende de `rouge >= 3.0, < 5.0`; fixar `gem 'rouge', '~> 5.1'` no Gemfile (feito sem `bundle install` local para validar, já que não há Ruby na sandbox) quebrou `bundle lock` no CI com "Could not find compatible versions" — corrigido para `~> 4.0`. Antes de fixar/subir a versão de uma gem que outra gem do Gemfile já depende transitivamente (hoje: `rouge` via `jekyll`), conferir a constraint da gem "pai" (`gem info <gem> --remote` ou a página da gem no RubyGems) em vez de só pegar a última versão publicada.
- Dependências (Gemfile e `package.json`) foram atualizadas para as últimas versões em 2026-08 — ver seção "Estado das dependências" acima antes de propor outro bump.
- **`sitemap.xml` e `feed.xml` não são mais arquivos manuais** (removidos na sessão de SEO, 2026-08) — agora são gerados pelas gems `jekyll-sitemap`/`jekyll-feed`. Não recriar esses arquivos na raiz do repo: os dois plugins só assumem a rota `/sitemap.xml`/`/feed.xml` quando **não existe** um arquivo-fonte com esse path; recriar um manual faz o plugin correspondente ser ignorado silenciosamente.
- **A chave de front-matter para excluir uma página do sitemap é `sitemap: false`, não `insitemap: false`.** `insitemap` era uma convenção do `sitemap.xml` manual antigo; `jekyll-sitemap` só reconhece `sitemap: false` (usado hoje em `404.html`, `search.json`, `msg-success.md`). Um novo `.md`/`.html` na raiz que precise ficar fora do sitemap deve usar `sitemap: false`.
- **`_config.yml` → `title`/`tagline` estão separados** (`title: Felipe Toscano` + `tagline: Diário de Bordo na Web`) desde a adoção do `jekyll-seo-tag`. Não voltar a juntar em `title: Felipe Toscano | Diário de Bordo na Web` — a tag `{% seo %}` já concatena `title`/`tagline` sozinha ao montar `<title>`/`og:site_name`; juntar os dois de novo duplica o "Diário de Bordo na Web" no `<title>` das páginas.
- **`CLAUDE.md`/`README.md` precisam ficar em `exclude:` no `_config.yml`.** Nenhum dos dois tem front-matter, e builds que carregam o plugin `jekyll-optional-front-matter` (caso do build legado do GitHub Pages via gem `github-pages`, não do nosso workflow) tratam `.md` sem front-matter como página processável por Liquid mesmo assim. Como este próprio arquivo cita `{% if post.category == page.category %}` como texto (ver bullet de `category:` acima), isso já quebrou o build com `Liquid::SyntaxError: 'if' tag was never closed`. Corrigido nesta sessão adicionando os dois ao `exclude:`; qualquer novo `.md` de documentação solto na raiz do repo (sem front-matter) deve entrar nessa mesma lista.

## Idioma e tom de voz

Conteúdo do blog é 100% em português (pt-BR); layouts usam `lang="pt-BR"`. Texto gerado para o site (posts, mensagens de UI, commits de conteúdo) deve ser em português.

- **Linguagem simples e profissional**: o público inclui gente ainda se familiarizando com o tema — evitar jargão desnecessário, explicar todo termo técnico na primeira menção, preferir frases curtas e diretas a parágrafos densos. "Profissional" aqui não é sinônimo de formal/acadêmico: o tom já estabelecido nos posts é conversacional, em segunda pessoa ("você"), como alguém explicando pra um colega — não como uma documentação seca ou um paper.
- **Minimizar a curva de aprendizado**: todo conceito novo vem acompanhado de um exemplo de código executável **e** de uma explicação em prosa do que o resultado significa — nunca só código sem explicação, nem só teoria sem exemplo. Evitar introduzir dois conceitos novos ao mesmo tempo sem necessidade; se um exemplo depende de algo ainda não visto, explicar isso rapidamente antes de usar. Progressão sempre do mais simples pro mais complexo dentro do próprio post (uso básico de uma função primeiro, variações/parâmetros avançados depois).
- **Maximizar engajamento**: abrir o post com uma frase de contexto ou analogia que conecte o tema a algo familiar antes de entrar em código; fechar com uma frase de ponte pro próximo post da série, dando senso de progressão contínua (ver seção "Séries de posts tutoriais" acima); usar `> **Nota:**` pra observações tipo "essa pegadinha" (armadilhas comuns, diferenças sutis, boas práticas) sem interromper o fluxo principal do texto.
- Essas diretrizes valem pra qualquer conteúdo gerado pro site — posts, descrições, textos de UI — não só pras séries tutoriais.
